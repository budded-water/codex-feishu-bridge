# Browser access blockage handoff

## Why

A real owner task and its verbal permission follow-up were blocked by Browser Use's saved origin denial even though native Auto-review passed. Conversation intent, native command authority and browser site authority are independent. The current bridge retains no structured browser denial or owner-linked continuation, and a fresh executor can encounter stale browser runtime variables.

## What changes

- Recognize only the installed Browser Use structured `persisted_user_denied` metadata and retain minimal origin/item/generation observations in the native journal.
- Show bounded historical observations, actual provider remediation and source-linked continuation through owner-private task views and a single durable post-settlement notice.
- Treat narrowly matched verbal browser-access consent as guidance, not a new model task or permission mutation.
- Accept an explicit owner `/browser-retry <execution> local-change-confirmed` only for an eligible completed ordinary task. Admit at most one linked fresh request per source; recheck sealed source at native startup and retain all existing native/browser authority.
- Initialize execution-local browser/runtime handles afresh on a new executor.

## Scope

The installed browser-control surface exposes no saved-site-approval management API; remediation remains in the desktop application's browser settings. Effective Codex origin restrictions can be inspected through supported read-only configuration APIs; a configuration allow is not a saved grant. No browser/settings rewrite, alternate-surface workaround, Guardian override, automatic retry, generic permission manager or business-delivery inference is added. Original tasks/journals remain immutable. Verification/repair tasks use their own fresh opt-in entry rather than inheriting plans or credits here. Existing pending permission, business and host gates remain separate.
