# 飞书事项与会话

在登记的本人私聊中，发送「换个话题，帮我看看小程序登录页」就能新建事项并交办第一条需求。也可以用「新对话：第一条需求」或「开个新话题，第一条需求」。新事项有独立会话，接下来直接发「游客模式呢？」会沿用它。使用 `/matter-new 事项名称` 可以先新建、再交办。用 `/matters` 找回并切换旧事项，也可以切回默认对话。第一次执行时才由 Codex 创建 thread。

- 回复原任务会按照原来的排队、执行中补充或收尾后追问规则处理。也可以直接回复 Bot 已确认送达的普通最终答案，在原事项中开始一轮追问。若正文的精确事项名前缀或绑定 PR 指向另一件事，机器人会先请你选择。选原事项时沿用原会话。选另一事项时，按该事项的新任务处理正文。回复单个事项卡片会使用该事项，即使当前选的是另一件事。早期未登记为续接入口的消息可以用原任务或事项卡片续接。
- 要补充某一轮正在执行的任务，可以回复那条原任务。无引用也无明确事项地址时，现有自然补充仍作用于正在执行的任务。选中了命名事项且没有任务正在执行时，「只查询」等只读请求会交给该事项。
- 发「事项名称：任务内容」可以按精确名称直达。名称与项目别名相同时，该前缀用于选择事项，执行范围仍由既有授权决定。若卡片和前缀指向不同事项，机器人会请你选择。选中一个命名事项后，用 `/matter-bind GitHub PR 链接` 登记它的关联对象。以后纯文本消息中包含该链接的任务会直接使用绑定的事项。
- 直接请 Bot 检查一个明确的 GitHub PR，可以用完整链接或「owner/repo PR #42」。已有绑定就直达原事项。单独交办未绑定 PR 的 CI、改动或合并状态等明确的只读查询时，会新建、绑定并切到新事项。背景链接和合并、发布等请求沿用既有入口。仅有项目昵称和编号而无法定位 PR 时，Bot 可以让你选择已有事项或开新。明确说「换个话题，……」会开一个独立事项，原 PR 的绑定仍可用来找回旧事项。已有事项的精确名称可继续用「事项名称：任务内容」直达。
- 「登录页也看看」这类既可能是补充、也可能是新事项的消息，会暂存并提供「本条发给」和「用这条消息开新话题」。选择已有事项只影响本条消息，选择新话题会把已保存的内容作为第一条任务。回执用「已新建」或「已续接」显示经核对的去向。
- 一条消息如果需要引用多个 PR 链接，可以用空格、换行或括号分别标出。链接的查询参数保留为该链接的一部分。
- 当输入指向多个可能的事项，或引用尚无法确认时，机器人先保存原消息并给出候选。点击后才会排队，只能处理一次。成功入队后，新的普通消息可以继续沿用该事项。候选过多时，可以引用相应事项卡片或明确填写事项名称再发。需要重发的旧消息会保留原决定。
- 「上一条的验收口令是什么？」优先沿用当前事项，几个事项共有的「验收」等字词不会单独触发选择卡。明确引用、事项地址和已绑定的 PR 仍优先。「刚才那个？」、「继续上一步」和「刚才那个改成周五」等未带明确引用的追问或修改会比较当前选中事项和最近入队的普通任务。修改消息里分别提到多个完整事项名时，选择卡会列出这些事项。「退款调查」只算一次提及，Alpha2 里的 Alpha 不算。如果有两个事项只差大小写，请分别按原名提及。后续分句或备选方案分别指向多个事项时，按普通路由给出相关事项。对之前改动的疑问仍按普通追问处理。以「也看看」结尾并符合新话题选择条件的补充消息仍会给出开新选项。引号里的替换文字不会被当作问句。参考链接里的参数也不会触发问句或事项匹配。「改成周五，时间不变」里的替换内容即使碰巧与其他事项共享标题词，机器人也会先比较当前事项和最近入队的普通任务。两者一致就直接续接，两者不同就先让你选。例如当前选中「发版」，刚回复过「退款」的旧答案，接着单发「继续上一步」，就会看到这两个候选。引用或明确指向其他事项时，当前选择会保留。点选确认归属或在当前事项明确交办任务后，可继续直接聊。接收回执会显示实际归属，包括默认对话。
- 事项归属决定普通任务的会话历史。引用内容发送 `/steer` 时，请引用运行中任务的原消息。审批、恢复、验证等专项命令使用各自的来源和授权。

AutoLoop 使用每次请求的 ID 派工，Bridge 决定续接哪个 thread。使用同一目录的任务由原有执行保护串行处理。

短追问按普通任务的入队顺序判断。飞书送达时间、验证任务和专项恢复不会改变这一判断。
