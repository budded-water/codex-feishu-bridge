# Codex 环境、工具与工作身份

bridge 把飞书请求送给运行电脑上的 `codex app-server`。它不包含一个独立的 Codex 账号，也不自动安装 GitHub、资料搜索、飞书文档等工具。

## 分身继承什么？

它使用运行账号可访问的本地 Codex 登录、配置、Skills / MCP 等工具配置以及项目规则。功能和权限仍取决于这些工具在 app-server 环境中的可用性。启动服务时 PATH、工作目录和运行账号要与实际安装一致；终端中可用的 UI 专属功能不保证 app-server 也可用。

bridge 为不同用户 / 聊天创建新 thread 并保存映射，之后恢复对应历史；不会自动附着到当前桌面会话，也不保证继承所有旧对话记忆。开发习惯、经验和 PR 工作流应记录在项目 `AGENTS.md`、长期文档和可访问的 Skills 中。群聊参考资料不作为执行或审批授权。

## GitHub、代码工作和资料搜索

实现功能、检查 diff、运行测试等在选中的项目目录发生；Git 和 GitHub 身份使用主机上工具的实际认证。bridge 不自带 GitHub token，也不替使用者创建代码工作流。

部署者应在每个项目写清 topic branch、检查、commit、push、开 PR、merge / 发布的授权规则，并验证本机工具选择的组织 / 个人账号正确。不要把开 PR 请求等同于合并授权。团队共用同一主机目录时会串行执行；独立并行工作树不是内置功能。

查资料依赖本机可用的搜索 / 浏览工具和资料访问权限。bridge 本身不是搜索引擎或知识库服务。业务数据源、查询入口和统计口径应维护在对应项目的规则和文档中；Codex 先核对这些信息，再选择 AWS CLI、数据库或分析工具，bridge 不硬编码产品与数据源的映射。讨论模式不能通过本机命令浏览仓库来猜前文，明确的项目任务可由 Codex 自动选择已登记项目；有歧义时澄清，也可用 `/project` 手动指定。

## 飞书 SDK 与飞书 CLI

| 部分 | 用途 | 发送 / 调用身份 |
| --- | --- | --- |
| bridge 内的飞书 SDK | 收消息、限定群上下文与图片、表情、投递答案 | `.env` 中的应用机器人身份 |
| 可选 `lark-cli` | Codex 按任务调用文档、消息、表格、日历等 API | CLI 选定应用下的 bot 或 OAuth user 身份 |
| 可选飞书 Skills | 指导 Codex 如何使用 CLI、格式和权限 | 不授予任何平台权限 |

不装 CLI，bridge 仍可收任务、做本地代码工作和回复。同一个飞书应用可以同时供 SDK 与 CLI 使用，不强制有两个 app；独立应用 / profile 可以便于管理不同权限，但不是主机隔离机制。

## 以部署者身份发消息

Codex 可另行调用 `lark-cli im +messages-send --as user`，以完成授权的本人身份发送。需要选定应用具备消息权限、本人完成 OAuth，以及有权访问目标会话；相关权限包括 `im:message.send_as_user` 和 `im:message`。以 bot 身份发送则是应用名义。检查当前登录与权限，不能把配置里存在一个用户记录当作凭据仍有效。[官方 CLI](https://github.com/larksuite/cli)

使用者需要明确收件人 / 群、发送内容和身份；未给出这些信息时先完成草稿和收件人核对。用户授权和 token 放在本机 CLI 的私有存储中，不能放入这个 public 仓库。

这是可选工具能力：bridge 不内置 OAuth 页面、每位同事的用户 token 管理、代发审批卡或自动把机器人回复切换成本人回复。取得用户授权后，bridge 的正常最终答案仍由机器人发送；要本人主动发送，需在具备工具权限的工作路径明确执行该动作。

## 同事触发任务时代表谁？

飞书提交者身份用于准入与会话归属。本机代码工具和 CLI 用户授权使用的是主机上所选凭据；同事 @机器人不会自动切换成这位同事的 GitHub / 飞书身份。例如 CLI 授权的是部署者，`--as user` 代表部署者。

同事能给分身提交工作，来自部署者明确委托的工作范围；仍需说明哪些资源和动作在范围内。会话分离不隔离文件、网络身份或凭据。需要严格隔离个人与团队能力时，应使用独立运行账号 / 凭据 / 工具接口或隔离环境；不能只靠换机器人名称、CLI profile 或提示词。

新部署者应使用自己的身份和资源。共享 bridge 代码，不会共享原部署者的开发经历、账号、聊天历史或工具授权。
